# KeePass 2 Windows Hello / quick-unlock alternatives (other than KeePassWinHello) and community discussion

Research date: 2026-10-18. Method: GitHub REST API dumps (all issues + all comments of Angelelz/WinHelloUnlock; issue lists of other repos; READMEs; selected source files read directly), keepass.info plugin list, SourceForge KeePass forum threads, ComputerBase forum, Microsoft Learn.
Evidence labels used below: **[body]** = I read the issue/thread body and comments; **[snippet]** = only the title plus the first ~200-350 characters of the body; **[code]** = read in the source code; **[readme]** = stated in the project README (author's claim, not verified by me).
Designs are described in my own words. No code is reproduced except short identifiers/messages.

## 1. WinHelloUnlock (Angelelz) and its forks: design, status, and all issues grouped by theme

### Takeaway
WinHelloUnlock (MIT, last release v1.6.1 on 2022-02-05) keeps a copy of the composite-key material permanently in the Windows Credential Locker (PasswordVault), encrypted with an AES key that is derived from a Windows Hello (KeyCredential) RSA signature over a fixed string. It has no expiry by design. Its 59 issues fall mostly into five groups: "incompatible plugin" reports that turned out to be install or config mistakes; Windows Hello, Vault or TPM errors that the developer could not reproduce; multi-PC sync breakage (probably caused by Credential Locker roaming; see Inferences); key components the plugin does not support (key providers like YubiKey, and the "remember master password" option being off); and prompt focus or UX problems. The #69 "database corrupted" report does not show that the plugin wrote to the database. The plugin's "delete key?" prompt shows up after KeePass has already failed to read the file, so it is a symptom, not the cause.

**Technical design** [code], from [UWPLibrary.cs](https://github.com/Angelelz/WinHelloUnlock/blob/master/WinHelloUnlock/UWPLibrary.cs), [Library.cs](https://github.com/Angelelz/WinHelloUnlock/blob/master/WinHelloUnlock/Library.cs), [WinHelloUnlockExt.cs](https://github.com/Angelelz/WinHelloUnlock/blob/master/WinHelloUnlock/WinHelloUnlockExt.cs), [csproj](https://github.com/Angelelz/WinHelloUnlock/blob/master/WinHelloUnlock/WinHelloUnlock.csproj)
- Ships as a plain DLL targeting .NET Framework 4.5. It calls WinRT through the NuGet packages Microsoft.Windows.SDK.Contracts and System.Runtime.WindowsRuntime, and references Windows.winmd (SDK 10.0.15063). There is no PLGX: the author could not make the UWP references work in a PLGX — [#22](https://github.com/Angelelz/WinHelloUnlock/issues/22) [body]
- **Identity = database path.** The KeyCredential name and the PasswordVault resource name are both the database path, with "/" replaced by "\\". The vault username is the product name "WinHelloUnlock". The source comment says that if the database is moved or renamed, new data has to be created.
- **Enrollment:** `KeyCredentialManager.RequestCreateAsync(dbPath, ReplaceExisting)` creates a per-database Hello key. The plugin then has that key sign a fixed message (the plugin assembly's GUID string) via `RequestSignAsync`. The raw signature bytes go straight into `SymmetricKeyAlgorithmProvider(AesEcbPkcs7).CreateSymmetricKey(...)`, with no KDF and no IV. ECB mode, no MAC or authentication tag.
- **What gets encrypted:** a serialized "KeyList" built from the open database's `CompositeKey.UserKeys`. For KcpPassword it stores the password itself, read back from KeePass's remembered key. For KcpKeyFile it stores **only the key file path**, not the key data. For KcpUserAccount it stores a marker string. Any other IUserKey (key providers such as KeeChallenge/YubiKey) is not supported. The ciphertext is Base64-encoded and saved as a `PasswordCredential(dbPath, "WinHelloUnlock", ciphertext)` in `PasswordVault`.
- **Unlock:** the plugin hooks `GlobalWindowManager.WindowAdded`, and when a `KeyPromptForm` appears it runs `KeyCredentialManager.OpenAsync(dbPath)` → `RequestSignAsync` (this is the Hello prompt) → rebuilds the AES key → decrypts → rebuilds the CompositeKey. It then calls `CheckMasterKey`, which **opens the whole database a second time in a scratch `PwDatabase`** and treats *any* exception as "wrong key". If that check fails, it asks "MasterKey must have changed. Delete WinHelloUnlock data?"
- **Detecting master-key changes:** on every `FileSaved` event the plugin runs `CheckMasterKey` again with the cached key, which means a full extra decrypt/KDF of the file after every save. If the check fails, it offers to update or delete the data. This came from a 2019 suggestion by Rookiestyle to use FileSaved, because KeePass has no "master key changed" event — [SourceForge "New Plugin: WinHelloUnlock"](https://sourceforge.net/p/keepass/discussion/329220/thread/2608a85e0e/)
- **Credential Locker behaviour (Microsoft docs):** credentials "roam between devices with the user's Microsoft account", "do not expire", and "you can only store up to 20 credentials per app". Microsoft also advises "Only use the credential locker for passwords and not for larger data blobs" — [Microsoft Learn: Credential locker](https://learn.microsoft.com/en-us/windows/apps/develop/security/credential-locker)

### Inferences
- **#53 and #46 multi-PC breakage is probably caused by Credential Locker roaming.** WinHelloUnlock names the vault entry (dbPath, "WinHelloUnlock"). Microsoft documents that such entries roam between devices on the same Microsoft account. When PC2 enrolls, its ciphertext (encrypted under PC2's Hello key) can overwrite PC1's entry. PC1 then decrypts garbage with its own key, and ECB/PKCS7 padding failure or the "CRC/data error" (0x80070017) message follows. This matches the reporters (same Microsoft account, same path) and why the author, who may have used a different setup, could not reproduce it. Not verified by experiment. A new plugin should keep per-device secrets in non-roaming local storage and should include a device or user identifier in the record.
- The 20-credentials-per-app Credential Locker limit would cap WinHelloUnlock at about 20 databases per user, if it applies to unpackaged desktop apps in the same way (not verified).
- Deriving an AES key directly from an RSA signature works only because RSA PKCS#1 v1.5 signatures are deterministic. It also ties decryptability to the exact signature format and to that particular Hello key. Any change that re-creates the Hello key (PIN reset, TPM clear, Hello re-enrollment, `ReplaceExisting` from a second enrollment) makes the stored ciphertext permanently undecryptable, with no integrity check to say why. There is no MAC, so a wrong key appears as a generic padding or "data error" (#53, #73) rather than a clear "this device's key changed" message.
- #69 most likely runs in the other direction from how it was reported: the .kdbx was already truncated (KeePass's own "data read … less than expected" error points to an incomplete write, and the reporter suspected low disk space). `CheckMasterKey` then failed, which triggered the plugin's misleading "MasterKey must have changed. Delete…?" prompt. Lesson: tell "wrong key" apart from "file unreadable or I/O error", and never phrase a prompt as if the user's key changed when the file simply could not be read.
- The 2.47 and 2.54 "breakage" is not a KeePass API break. It is (a) a renamed DLL, which violates KeePass's file-name/namespace rule, (b) outdated KeePass.exe.config, (c) running an old KeePass copy, or (d) a stored key file path that no longer exists. A new plugin should check its own file name and show a friendly error, and should never persist ephemeral key file paths.
- The 0x8028008B TPM error on the first start of the day, together with the Fast Startup workaround, suggests the TPM or Hello service was not ready after a hybrid boot. A new plugin should retry or back off once on TPM-class HRESULTs before giving up, and should explain the Fast Startup workaround.
- Storing only the key file *path* means quick unlock silently depends on that file still being present, which is both a reliability problem (#54) and a source of confusion. The LockAssist 2025 corruption shows the worst case: saving a database under a composite key that was rebuilt incorrectly. A new plugin should verify the reconstructed key against the database header before letting KeePass save anything.

### Gaps
- I could not view the screenshots in #59, #68, #69 (first one), #46, #53 or #73, so the exact dialog texts beyond what users typed are unknown.
- WinHelloUnlock download counts were not retrieved, because the API rate limit was reached.
- I could not confirm whether `CreateSymmetricKey` with a 256-byte signature buffer behaves as AES-256 or does something else internally (Microsoft docs not checked).
- Whether the Credential Locker's 20-credential limit applies per unpackaged Win32 app was not verified.
- KeePass 2.47's own change log was not checked for a plugin-relevant change. The only concrete 2.47 evidence is the key file path exception.

## 2. Other KeePass 2 quick-unlock / Windows Hello / biometric / PIN plugins (excluding KeePassWinHello)

### Takeaway
Besides KeePassWinHello and WinHelloUnlock, the official plugin list now includes three Hello/TPM-capable key stores: KeePassProtectedKeyStore (2024), KeePassPasskeyKeyProvider (2026) and the DPAPI-based WinKee and KeePassAutoUnlock. It also lists two in-memory "short PIN" quick-unlock plugins, KeePassQuickUnlock (stale since 2018) and LockAssist (actively maintained in 2026). Several brand-new 2026 projects use FIDO2 hmac-secret/PRF with multiple authenticators and recovery options. Older GitHub experiments (kpbio, KeePassFingerprint, KuhlKuh, KeeBiometrics, KeePassWindowsHello by fabiocbr75) are abandoned or never shipped. I found no plugins named "KeeHello", "KeePass Biometric" or "WindowsHelloKeyProvider".

### Cited Findings

**Official plugin list entries relevant to this topic**, from [keepass.info/plugins.html](https://keepass.info/plugins.html), "Cryptography & Key Providers" section:
- KeePassWinHello (Sasha Sitnikov, Andrey Osipkov). Out of scope here.
- WinHelloUnlock (Angelelz): "Manages database access credentials using Windows Hello"
- KeePassQuickUnlock (Janis Estelmann): "Unlocks databases quickly."
- LockAssist (Rookiestyle): "Unlocks databases quickly."
- KeePassProtectedKeyStore (CSquared167): "Creates and uses protected key stores", with the note that it uses Windows Hello or DPAPI
- WinKee (Theo Beisch): "Manages database access credentials", encrypting them with DPAPI against the Windows account. The only link is a ZIP download (WinKee-2.39.1)
- KeePassAutoUnlock (Jérémy Bourgin): "Opens a database when starting KeePass" (DPAPI)
- KeePassPasskeyKeyProvider (Grigory Ermolaev): "Key provider based on passkeys" (FIDO2 key, phone via QR, or Windows Hello)
- KeePassPasskey (Uwe Kögel, in the Integration section) stores website passkeys in KeePass and is not an unlock method

**KeePassProtectedKeyStore (CSquared167)**: MIT, created 2024-04-12, last push 2026-06-20, 20 stars, latest version 1.5.0 — [GitHub](https://github.com/CSquared167/KeePassProtectedKeyStore)
- Design [readme+code]: registers as a **key provider**. It converts existing key components (master password, Windows user account, and/or key provider output) into a "protected key store" file under `%LOCALAPPDATA%\CSquared167\KeePassProtectedKeyStore`. It offers either a DPAPI engine (`ProtectedData`, CurrentUser scope, with entropy) or a Windows Hello engine. It can make an **emergency key recovery file**, which can be imported on another PC. It has optional auto-login when the key store is the only key component. It keeps per-database or default stores, works per Windows user and PC for shared NAS databases, and does not support portable KeePass — [README](https://github.com/CSquared167/KeePassProtectedKeyStore)
- Hello engine [code]: one KeyCredential named after the plugin (opened, or created with `ReplaceExisting`). It signs a fixed 16-byte constant, and the signature becomes an AES-**CBC**-PKCS7 key through `CreateSymmetricKey`. This is the same "signature as key" idea as WinHelloUnlock, but with one credential shared across all databases. A background thread polls `FindWindow("Credential Dialog Xaml Host")` every 100 ms and calls `SetForegroundWindow` on it in a loop. It also shows an off-screen "hidden" modeless dialog so that KeePass gets the foreground back afterwards. The code comment calls these "workarounds [that] cannot be guaranteed to work 100% of the time" and says they depend on the Hello dialog's class name — [EncryptionEngine.cs](https://github.com/CSquared167/KeePassProtectedKeyStore/blob/master/KeePassProtectedKeyStore/EncryptionEngine.cs)
- Issues (6 in total) [snippet unless noted]: #1 (2025) opening multiple databases with Hello replaces the focused database. #2 (2025) "Unable to create protected key store" after the Hello prompt (German Windows). #3 and #4 (2026) auto-unlock path breaks AutoExec, "database opened" triggers, and `MainWindow.FileOpened` (KeeAgent did not load keys). #5 (2026) portable version fails. **#6 (opened 2026-10-18, open) [body]:** on KeePass 2.61.1 (32-bit) with Windows 11 build 10.0.26300, the Hello prompt "appears and then closes right away", and on the startup auto-login path KeePass hangs and must be killed — [issues](https://github.com/CSquared167/KeePassProtectedKeyStore/issues), [#6](https://github.com/CSquared167/KeePassProtectedKeyStore/issues/6). (Note: 26300 is also this research machine's Windows build.)

**KeePassPasskeyKeyProvider (brlumen / Grigory Ermolaev)**: MIT, created 2026-09-24, v1.0.0 on 2026-09-29, v1.0.1 on 2026-09-30, pushed 2026-10-18 — [GitHub](https://github.com/brlumen/KeePassPasskeyKeyProvider) [readme]
- A key provider that uses the native Windows WebAuthn API with the hmac-secret/PRF extension. The database is locked with a random 256-bit key, wrapped per device (security key, phone via QR/caBLE, or Windows Hello). It supports multiple devices, device revocation (rotating the database key), a 12-word BIP39 recovery phrase, master-key change without re-enrolling devices, and signed device records. **All data is stored inside the .kdbx**, with no side files. It can be combined with password or key file. Requirements: Windows 11 22H2+ (WebAuthn API v4+), KeePass 2.52+, KDBX 4
- This approach changes the database's master key composition, so it is not a "quick unlock" layered on top of an unchanged master key

**KeePass FIDO2 (Helveg/keepass-fido2)**: GPL-3.0, created 2026-09-17, v0.1.0–v0.3.0 (last 2026-10-05), "early development" — [GitHub](https://github.com/Helveg/keepass-fido2) [readme]
- Leaves the master key unchanged. It captures the *derived* key data (for a password, KeePass's SHA-256 of it, not the plaintext) and encrypts that snapshot with a random data key (AES-256-CBC + HMAC-SHA256). It wraps the data key once per method: a FIDO2 resident credential's hmac-secret with a per-database salt, and/or a Windows Hello RSA key in the TPM via the Microsoft Passport KSP, created so that every use requires a Hello gesture. It adds "Windows Hello" and "Security key" buttons to the key prompt, with an optional auto-start of Hello. When the master key changes, entering it once re-wraps all methods. Data lives in `%LOCALAPPDATA%\keepass-fido2\unlock.xml` (ciphertext + credential IDs). The README includes a threat table that states openly that someone with the laptop *and* the Hello PIN can unlock. It also has a `kp run` helper for secrets in env files

**KeePassQuickUnlock (JanisEst / Janis Estelmann)**: MIT, created 2016-06-13, last release v2.4 on 2018-04-10, last push 2019-09-25, 139 stars, 47 issues (11 open) — [GitHub](https://github.com/JanisEst/KeePassQuickUnlock) [readme]
- Design: a short quick-unlock code replaces the full key only after the database has been opened once in the current KeePass session. The data lives **only in memory** and is lost when KeePass exits. Two modes: (1) the code comes from an entry titled "QuickUnlock", or (2) "PartOf" mode, where the code is part of the master password and works only once per full unlock because of KeePass key-handling limits. One wrong code invalidates it. Since v2.4 the master key is encrypted with the quick code instead of being compared — [README](https://github.com/JanisEst/KeePassQuickUnlock); [#26](https://github.com/JanisEst/KeePassQuickUnlock/issues/26) [snippet]
- Recurring complaints [snippet]: not available after restarting KeePass (#4 2016, #18 2017, #21 2017, #33 2019). "PIN unlock?" like Windows (#5 2016). Wants longer expiry such as 3 days or a week (#17 2017, #25). Timeout does not count standby time (#38 2019). Key file path lost or removed from config (#13, #19, #27, #40 2016–2021). PartOf mode broken in 2.41 (#34). Linux/Mono incompatibility (#1, #12, #31). Conflict with the SmartCertificate key provider (#43 2021). "Is this project still active?" (#47 2025) — [issues](https://github.com/JanisEst/KeePassQuickUnlock/issues)
- The Chocolatey package `keepass-plugin-quickunlock` 2.4.0 page shows "rejected on 10 Oct 2022" (reason not shown) — [Chocolatey](https://chocolatey.org/packages/keepass-plugin-quickunlock/2.4.0)

**LockAssist (Rookiestyle)**: GPL-3.0, created 2021-08-24, v3.10 released 2026-08-29 (v3.8 2025-09, v3.9 2026-02, v3.9.1 2026-04), 52 stars, 0 open issues, PLGX — [GitHub](https://github.com/Rookiestyle/LockAssist) [readme]
- Design: in-memory quick unlock with a short key, either from a "LockAssist - Quick Unlock" entry or from part of the database password. It also offers SoftLock (privacy mode that hides the UI but keeps Auto-Type working) and global lock/unlock of all databases. It works only for a database that is still loaded and locked, not after a reboot, which is the author's own explanation in [#4](https://github.com/Rookiestyle/LockAssist/issues/4) [body]
- Issues and wishes [snippet unless noted]: global hotkey for quick unlock without showing the window (#5 2021). More than one attempt before falling back to the full password (#17 2024, added in v3.8). Unresponsive PIN entry (#18 2024). NullReferenceException in `RestoreOldMasterKeyInternal` (#24, #25 2026). Broken on a KeePass dev build (#22 2026) and on Arch Linux 2.61 (#30 2026). Key-file data-loss path, see section 1 (#4, 2021 and 2025) [body]

**DPAPI-only "auto unlock" plugins (no biometrics)**

It stores the master password encrypted for the current Windows user and opens the database at KeePass start. The README states the account itself, protected by password or Windows Hello, is what guards the database — [GitHub](https://github.com/jeremy-bourgin/KeePassAutoUnlock) [readme]

- ChiefGokhlayeh/KeeBiometrics (Apache-2.0, archived, last push 2020-03-04, "DRAFT"): a key provider plus Android app that sends a secret over mutually authenticated TLS after phone biometrics — [GitHub](https://github.com/ChiefGokhlayeh/KeeBiometrics)
- Uranium235/kp-quickunlock (GPL-3.0, 2014): empty repo. xt9852/KeePassXT (2016–2017): a patch to KeePass **1.x** (C++) using the Windows Biometric Framework, not a KeePass 2 plugin — [kp-quickunlock](https://github.com/Uranium235/kp-quickunlock), [KeePassXT](https://github.com/xt9852/KeePassXT)

**Non-plugin reference point: KeePassXC**
- KeePassXC 2.7.0 (March 2022) added native Windows Hello quick unlock. It is enabled by default on Windows, and setting it up requires a full unlock first — [gHacks 2022-03-01](https://www.ghacks.net/2022/03/01/keepassxc-adds-support-for-windows-hello-touch-id-apple-watch/); [KeePassXC User Guide](https://keepassxc.org/docs/KeePassXC_UserGuide)
- After a restart KeePassXC still shows the normal password dialog first, and Hello only applies after that (issue #7570, KeePassXC 2.7.0). There is also a request to turn the option off by default on machines without Hello (#10369) — [#7570](https://github.com/keepassxreboot/keepassxc/issues/7570), [#10369](https://github.com/keepassxreboot/keepassxc/issues/10369) [snippet via search summary]
- KeePassXC's implementation (PR #7384) signs a challenge with the TPM-backed Hello key and uses the result to encrypt the database credentials — [PR #7384](https://github.com/keepassxreboot/keepassxc/pull/7384) [snippet via search summary]

### Inferences
- The field splits into three architectures. (1) **Session-only quick unlock**: KeePassQuickUnlock, LockAssist, and KeePassXC's Hello mode. These are safe against offline theft but useless after a reboot, which is the most common complaint. (2) **Persistent wrapped secret** that survives reboots: WinHelloUnlock (PasswordVault), KeePassProtectedKeyStore (files), KeePass FIDO2 (unlock.xml), and the DPAPI plugins. These are convenient but turn the Windows Hello PIN into an alternate key, and they need recovery and invalidation handling. (3) **Authenticator as a real master-key component**: KeePassPasskeyKeyProvider and the YubiKey-style providers. These change the database itself and affect sharing with clients that don't have the plugin.
- Two newer independent projects (KeePassProtectedKeyStore, KeePass FIDO2) each re-implemented "Hello signature → symmetric key" or a TPM RSA key, and both added foreground/focus hacks or start-on-prompt options. Dialog focus is a cross-cutting pain point that every implementation has to solve and that tends to break across Windows builds (see KeePassProtectedKeyStore #6 in 2026).
- Features that recent projects treat as table stakes: multiple unlock methods per database, a recovery path (emergency file or BIP39 phrase), automatic re-wrap on master-key change, storing derived key data instead of the plaintext password (KeePass FIDO2), and an explicit threat-model table.

### Gaps
- WinKee's design and status could not be checked beyond the plugin-list note (no website, ZIP only).
- I did not read the KeePassQuickUnlock and LockAssist wiki pages that justify their security arguments.
- KeePass FIDO2 and KeePassPasskeyKeyProvider are only weeks old (Sept–Oct 2026). Their stability and their uptake by users are unknown.
- I did not verify whether the KN4CK3R/KeePassQuickUnlock repo (seen in search results) is the same author's account or a fork.
- No evidence was found for any plugins named "KeeHello", "KeePass Biometric" or "WindowsHelloKeyProvider". The GitHub search terms I used were "keepass windows hello", "keepass hello plugin", "keepass quick unlock", "keepass quickunlock", "keepass biometric", "keepass fingerprint", "keepass tpm", "keepass2 hello", "keepass passkey unlock" and "keepass fido2 plugin".

## 3. Community complaints, wishes and fears about biometric / Windows Hello unlock in KeePass 2

### Takeaway
The single most repeated wish is **unlock by Hello on the first open after a reboot**, not just after a lock. Session-only tools (KeePassWinHello's default mode, QuickUnlock, LockAssist, KeePassXC) disappoint on exactly this point. The fears are mostly these: the Windows Hello PIN or PC password becomes a weaker back door to a strong master password; trust in the plugin authors and in Windows Hello as a black box; poor plugin maintenance; locking yourself out; and admins who forbid plugins (hence requests for native support). People who moved to KeePassXC cite native Hello and YubiKey support, but KeePassXC also requires the full password after a restart.

### Cited Findings
**Wishes**
- 2019-03-09, SourceForge: a user wants Windows Hello "for the first unlock, such as after a reboot". KeePassWinHello only covered re-authorisation after the first unlock — [SourceForge 31b108bce4](https://sourceforge.net/p/keepass/discussion/329220/thread/31b108bce4/)
- 2017-02-04 to 2017-02-09, SourceForge: a user asked for Hello face logon. A moderator said KeePass doesn't integrate with Windows logon beyond the Windows User Account (WUA) key option, and that a plugin would be needed — [SourceForge e72734cc](https://sourceforge.net/p/keepass/discussion/329220/thread/e72734cc/)
- **2024-10-17, SourceForge: a user wants native Hello support "because some admins don't allow plugins"** and calls the plugins poorly maintained, with KeePassWinHello carrying an unfixed bug. On 2024-10-19 they rejected WUA because it does not work across multiple devices synced through OneDrive. They pointed to iOS, where the Secure Enclave protects the password — same thread
- ComputerBase (German), 2021-12-16: with KeePassWinHello the master password is still needed on the first start after boot, and one user dropped it because "the master password is still required after a reboot, which is when it is needed most". 2024-06: users want fingerprint or PIN alone after a reboot; one user had used KeePassWinHello with a laptop reader for years; another switched to KeePassXC for native YubiKey support — [ComputerBase thread](https://www.computerbase.de/forum/threads/usb-fingerprintsensor-fuer-keepassanmeldung-und-optional-firefoxanmeldungen-gesucht.2059152/)
- WinHelloUnlock users ask for: multiple PCs with the same database (#53), multiple users (#70), a choice of Hello modality (#8), YubiKey/MFA composite support (#62), AutoType on unlock (#31, #56), Chocolatey packaging (#15), no error popup when the user cancels (#48), and ongoing maintenance (#83) — see section 1
- QuickUnlock and LockAssist users ask for: survival across a KeePass restart, a Windows-style PIN, longer expiry (days or a week), timeouts that count standby, more than one attempt, and a global hotkey — see section 2

**Fears and concerns**
- **The fallback becomes the weak link:** "if Windows Hello recognition fails, the fallback is your PC's password, *NOT* your KeePass database's … password. It's def a security vs. convenience tradeoff" (jdrch, 2021-10-18) — [WinHelloUnlock #53](https://github.com/Angelelz/WinHelloUnlock/issues/53) [body]
- **Trust in the plugin author:** in a 2024-10-06 SourceForge thread comparing WinHelloUnlock, KeePassWinHello and KeePassProtectedKeyStore, the original poster questioned WinHelloUnlock's security because its README says "I am not a programmer, so I copied most of the code". They were unsure whether KeePassWinHello is maintained, and noted that nobody had discussed KeePassProtectedKeyStore yet — [SourceForge c53b30ce59](https://sourceforge.net/p/keepass/discussion/329220/thread/c53b30ce59/)
- **Lock-out risk and "is it worth it":** in the same thread, a reply (2024-10-06) prefers a long master password plus KeePassQuickUnlock: "I don't need Auto-Login just to avoid typing my full password once a day", and calls the risk of losing access too high. Another reply (2024-10-18): "The harder you make it the one to loose access is yourself" — same thread
- **The Hello black box:** in 2019 Dominik Reichl said it was "still not clear to me how exactly Windows Hello works" (roles of DPAPI, TPM, Microsoft account). The WinHelloUnlock author conceded that the key ends up in a Microsoft "black box" — [SourceForge 2608a85e0e](https://sourceforge.net/p/keepass/discussion/329220/thread/2608a85e0e/)
- **Unattended unlocked PC:** a 2020 user argued that the bare Windows account (WinKee/WUA) is weaker than requiring the Hello PIN, because someone at an unlocked PC could open KeePass. Others replied that KeePass auto-locks — [SourceForge 943adddaaf](https://sourceforge.net/p/keepass/discussion/329220/thread/943adddaaf/?limit=25)
- **Key file hygiene in related advice:** a 2024 reply warns that a key file must never sit next to or sync with the database — [SourceForge e72734cc](https://sourceforge.net/p/keepass/discussion/329220/thread/e72734cc/)
- A PCWelt (German) how-to on KeePassWinHello notes that very security-conscious users may be put off by storing the master password in the Windows Credential Manager (search-result summary only, page not fetched) — [PCWelt](https://www.pcwelt.de/tipps/Passwortmanager-Keepass-mit-Windows-Hello-starten-10955903.html)

**Operational complaints seen across plugins**
- The Hello dialog appears behind KeePass or loses focus (WinHelloUnlock #1/#11 in 2019 and #82 in 2025; KeePassProtectedKeyStore's code workarounds and its 2026 #6). KeePass is minimized to the tray after a Hello login with KeePassWinHello 3.3.1 on Windows 11 and KeePass 2.56 (SourceForge, 2024) — [SourceForge 580cb674b9](https://sourceforge.net/p/keepass/discussion/329220/thread/580cb674b9/) (title and search summary only)
- Error popups on PCs without Hello (Windows 7, or Windows 10 with Hello off) for KeePassWinHello, where the setting cannot be disabled. Dominik replied on 2024-03-21: "Please report this issue to the developers of the KeePassWinHello plugin." — [SourceForge a893a3d9f9](https://sourceforge.net/p/keepass/discussion/329221/thread/a893a3d9f9/)
- Behaviour after Windows updates, TPM errors on first start, corporate-managed PCs blocking the vault, and secure-desktop conflicts (WinHelloUnlock #73, #67, #61, #77)

**Why some move to KeePassXC**
- Native Hello quick unlock since 2.7.0 (2022) with no plugin, and native YubiKey challenge-response (ComputerBase user, 2021) — [gHacks](https://www.ghacks.net/2022/03/01/keepassxc-adds-support-for-windows-hello-touch-id-apple-watch/); [ComputerBase](https://www.computerbase.de/forum/threads/usb-fingerprintsensor-fuer-keepassanmeldung-und-optional-firefoxanmeldungen-gesucht.2059152/)
- Counterpoint: KeePassXC also asks for the master password first after a restart (#7570), which a ComputerBase user called illogical in 2024-06. A WinHelloUnlock user asked whether the DLL works in KeePassXC (it does not; #80) — [KeePassXC #7570](https://github.com/keepassxreboot/keepassxc/issues/7570); [WinHelloUnlock #80](https://github.com/Angelelz/WinHelloUnlock/issues/80)

### Inferences
- A design that offers *optional* persistent (post-reboot) Hello unlock answers the top wish. It has to make the trade-off explicit: whoever passes Windows Hello on this PC, including with the Hello PIN, can open the database. It should also offer a "session-only" mode for the cautious majority.
- Admin-managed environments both block plugins and break Credential Locker/TPM calls (#61). Clear diagnostics and graceful fallback to the normal key prompt matter more than adding features.
- Maintenance signals (recent releases, an answered issue tracker, signed DLLs, a Chocolatey or winget package, an update-check URL) clearly influence trust in these discussions.

### Gaps
- **Reddit could not be accessed.** reddit.com blocked both the search tool and direct JSON requests, so no r/KeePass, r/privacy or r/sysadmin threads are included.
- No Dr. Windows (drwindows.de) thread was found. Only one ComputerBase thread was read.
- No Stack Exchange (Super User / Security.SE) threads on KeePass 2 + Windows Hello were found within the search budget.
- The SourceForge "feature-requests" tracker (as opposed to the discussion forums) was not searched directly.

## 4. Dominik Reichl's position on Windows Hello / built-in support

### Takeaway
I found no official statement promising built-in Windows Hello support. In 2019 Dominik Reichl explicitly said "I'm not planning to implement this" and pointed people to plugins. He lists Hello and passkey plugins on keepass.info. He sends plugin bug reports to the plugin authors. He has questioned how a Hello plugin differs in security from KeePass's built-in Windows User Account option.

### Cited Findings
- 2019-03-09, on a Hello-for-first-unlock request: "There already exists a plugin for this, namely KeePassWinHello." Followed by: "I'm not planning to implement this", with the suggestion to ask the KeePassWinHello developer — [SourceForge 31b108bce4](https://sourceforge.net/p/keepass/discussion/329220/thread/31b108bce4/)
- 2018-08-28, on the KeePassWinHello announcement: "Interesting plugin, thanks!" He added it to the plugins page — [SourceForge 087b5d99](https://sourceforge.net/p/keepass/discussion/329220/thread/087b5d99/)
- 2019-07-19, on the WinHelloUnlock announcement: "From a security point of view, what's the difference between your plugin and the built-in Windows user account option?" On 2019-08-04 he wrote that it was "still not clear to me how exactly Windows Hello works" (DPAPI, TPM, Microsoft account), and added the plugin to the list anyway — [SourceForge 2608a85e0e](https://sourceforge.net/p/keepass/discussion/329220/thread/2608a85e0e/)
- 2024-03-21: "Please report this issue to the developers of the KeePassWinHello plugin." — [SourceForge a893a3d9f9](https://sourceforge.net/p/keepass/discussion/329221/thread/a893a3d9f9/)
- 2018-06: he added "Remember master password (in encrypted form) of a database while it is open" and warned "We might see some plugins crashing when the option is turned off", recommending that users re-enable it in that case. WinHelloUnlock depends on this option (#37, #82) — [SourceForge 62b0b650](https://sourceforge.net/p/keepass/discussion/329220/thread/62b0b650/)
- The KeePass plugin docs recommend shipping a DLL ("DLL plugins are better, because they can be digitally signed (Authenticode)") and supporting the update-check version file via `UpdateUrl` — [KeePass plugin development](https://keepass.info/help/v2_dev/plg_index.html)
- keepass.info now lists Hello/TPM/passkey options (KeePassWinHello, WinHelloUnlock, KeePassProtectedKeyStore, KeePassPasskeyKeyProvider) — [plugins.html](https://keepass.info/plugins.html)

### Inferences
- Built-in Windows Hello support in KeePass 2 looks unlikely. A new plugin should target KeePass's existing extension points (key provider and/or KeyPromptForm interception, the FileSaved and FileOpened events), avoid depending on the "remember master password" option where possible (or detect it and explain it clearly), and be ready to answer Dominik's question about how it differs from the built-in Windows User Account option.

### Gaps
- I found no post from Dominik after 2019 that directly assesses Windows Hello or passkey unlock, and no KeePass changelog entry adding Hello-related APIs (KeePass 2.5x/2.6x changelogs not checked).
- The SourceForge feature-request tracker was not searched for a Hello ticket and any status Dominik assigned to it.
