# Build RamzX Unlock on signed, expiring envelopes

Research date: 2026-10-18. Scope: Windows Hello, quick-unlock and YubiKey solutions for KeePass 2 and KeePassXC, and what they imply for "RamzX Unlock" (KeePass 2 plugin, C#, .NET Framework 4.8, MIT, written from scratch). The designs of other projects are described in prose only. No code from any of them is to be copied.

Users of existing Windows Hello unlock tools rarely complain about cryptography. Their complaints are that the Hello prompt fails, hides or vanishes after a Windows update, that quick unlock does not survive a KeePass restart, and that nobody fixes the bugs. The reference plugin, KeePassWinHello (369 stars), has **45 of its 110 issues in NCrypt/TPM error dialogs**. Among them are **14 reports of face unlock failing with 0x80098044**, and no release since v3.3.1 (2024-04-07) fixes them. KeePassXC has pushed persistent Windows Hello unlock back to v2.9.0 and rejects expiry requests. Searches found no KeePass 2 plugin that uses KeePassXC-compatible YubiKey challenge-response. Each of RamzX Unlock's goals answers a documented, unmet request: survival across KeePass restarts, absolute expiry, locking together with Windows, and a KeePassXC-format YubiKey factor. The evidence points to a design built on documented APIs:

1. A KeyCredentialManager key signs a random challenge stored with each record.
2. The signature is turned into a symmetric key.
3. That key wraps the database's *derived* key components.
4. The result is stored only as ciphertext in a local, non-roaming file. It expires after a reboot or after X days, and it sits on top of an unchanged KeePass master key.

This can be built for .NET Framework 4.8, but two behaviours are undocumented and must be measured first. One is whether Hello signatures are deterministic: two Microsoft pages contradict each other. The other is whether the prompt stays visible. KeePassProtectedKeyStore #6, filed today on the same Windows build 26300 that this machine runs, reports a Hello prompt that closes immediately. Windows Hello always allows a PIN fallback, so the Hello part is a convenience lock, not a second factor. The YubiKey part can be a real factor. But KeePass re-randomizes the KDF seed on every save, so a naive implementation would write databases that nobody can open.

That includes all 110 KeePassWinHello issues with their 315 comments, all 59 WinHelloUnlock issues, about 70 KeePassXC Windows Hello issues and pull requests, and the 25 newest KeeChallenge issues. Grouped by theme, they show a consistent picture: the user experience around the Hello prompt and the key lifecycle breaks far more often than the encryption does. **Theme 1, error codes, is the largest cluster.** In KeePassWinHello the headline code `0x80098044` is `WINBIO_E_INVALID_TICKET`. It appears in SDK metadata but not in Microsoft's public WinBio error table ([windows-rs metadata](https://raw.githubusercontent.com/microsoft/windows-rs/0.59.0/crates/libs/sys/src/Windows/Win32/Devices/BiometricFramework/mod.rs)). The pattern points to the authorization gesture, not to a damaged key: face fails on the first prompt after a fresh KeePass start, while PIN decrypts the same key ([#120](https://github.com/sirAndros/KeePassWinHello/issues/120)). One contributor reproduces the failure every time. In his tests a standalone console harness never fails, and he attributes the failure to the Hello dialog losing the foreground while KeePass windows appear ([PR #159](https://github.com/sirAndros/KeePassWinHello/pull/159)). The other error clusters have identifiable triggers:

- NGC keys disappear after a PIN reset or TPM reset ([#60](https://github.com/sirAndros/KeePassWinHello/issues/60), [#160](https://github.com/sirAndros/KeePassWinHello/issues/160)).
- Errors appear after a Windows Update and go away after re-enrolling the fingerprint ([#121](https://github.com/sirAndros/KeePassWinHello/issues/121)).
- The TPM is not ready on the first start of the day, which a user fixed by disabling Fast Startup ([WHU #67](https://github.com/Angelelz/WinHelloUnlock/issues/67)).
- Errors happen at lock or close time because KeePassWinHello re-encrypts and re-stores the key on every lock ([#129](https://github.com/sirAndros/KeePassWinHello/issues/129), [#161](https://github.com/sirAndros/KeePassWinHello/issues/161), [#67](https://github.com/sirAndros/KeePassWinHello/issues/67)).

At least eight recent KeePassWinHello reports are empty templates. That follows from a generic "something went wrong, please report" dialog that opens a new GitHub issue ([PR #74](https://github.com/sirAndros/KeePassWinHello/pull/74)). Users would be better served by a plain-language recovery message.

**Theme 2, focus, is the longest-running UX failure and it affects every implementation.** It shows up in several forms:

- KeePassWinHello's prompt sits behind KeePass when it is triggered by the Auto-Type hotkey. Two users switched to KeePassXC over this ([#86](https://github.com/sirAndros/KeePassWinHello/issues/86)).
- The plugin's foreground helper searches for the English dialog title "Windows Security", so it never matches on German Windows ([PR #163](https://github.com/sirAndros/KeePassWinHello/pull/163)).
- KeePassXC brings the dialog forward with a timer that looks for the "Credential Dialog Xaml Host" window class. Users on Windows 11 24H2 still see the prompt behind the app when the browser extension triggers it, and those reports were closed as not planned ([#11864](https://github.com/keepassxreboot/keepassxc/issues/11864), [#10175](https://github.com/keepassxreboot/keepassxc/issues/10175)).
- KeePassProtectedKeyStore polls for the same window class every 100 ms. Its own code comment says the workaround cannot be guaranteed ([EncryptionEngine.cs](https://github.com/CSquared167/KeePassProtectedKeyStore/blob/master/KeePassProtectedKeyStore/EncryptionEngine.cs)).

On a tray-minimized KeePass, the approach that worked was to bring KeePass's own main window forward first, by attaching to the foreground thread's input. Matching the Hello window alone was not enough ([#86 comment](https://github.com/sirAndros/KeePassWinHello/issues/86)).

**Themes 3 and 4 show the market gap.** In the forums, the most repeated wish is Hello unlock on the first open after a reboot ([SourceForge](https://sourceforge.net/p/keepass/discussion/329220/thread/31b108bce4/), [ComputerBase](https://www.computerbase.de/forum/threads/usb-fingerprintsensor-fuer-keepassanmeldung-und-optional-firefoxanmeldungen-gesucht.2059152/)). KeePassXC keeps quick unlock only in process memory, by design ([#7570](https://github.com/keepassxreboot/keepassxc/issues/7570)). Its "Remember Quick Unlock" pull request has been open since December 2024 and was moved to the v2.9.0 milestone on 2026-09-13 ([PR #11520](https://github.com/keepassxreboot/keepassxc/pull/11520)). The current stable release is 2.7.12, and 2.8.0-beta1 adds no Windows Hello changes ([CHANGELOG](https://github.com/keepassxreboot/keepassxc/blob/develop/CHANGELOG.md)). KeePassXC also refuses configurable expiry ([#12853](https://github.com/keepassxreboot/keepassxc/issues/12853)). Among KeePass 2 plugins, WinHelloUnlock persists the key but never expires it ([ReadMe](https://github.com/Angelelz/WinHelloUnlock/blob/master/ReadMe.md)). KeePassWinHello persists with a 24-hour default, but its expiry was reset on every lock until a 2026 fork fixed it ([cuprum-72](https://github.com/cuprum-72/KeePassWinHello/commits/master)).

RamzX Unlock's design (keep the key across KeePass restarts, expire after a reboot or after X days) sits between these two camps. It deliberately does *not* meet the "after reboot" wish by default. That is a defensible choice, but it should be stated plainly as one.

**Theme 5 shows that how enrollment is presented determines whether users trust the feature.** About 14 KeePassXC issues call the feature a "bypass". In those cases the user cancelled the Hello prompt that appears *after* a full password unlock, and the database opened anyway. The prompt was arming quick unlock, not guarding the database ([#7886](https://github.com/keepassxreboot/keepassxc/issues/7886), [#12376](https://github.com/keepassxreboot/keepassxc/issues/12376)). The default-on checkbox, which is greyed out on some machines, drove away at least one enterprise deployer ([#10369](https://github.com/keepassxreboot/keepassxc/issues/10369)). Explicit, per-database opt-in avoids both problems.

**Themes 7 and 10 contain the data-safety lessons.** WinHelloUnlock stores the key-file *path* rather than its content, so unlock fails when the path disappears ([#54](https://github.com/Angelelz/WinHelloUnlock/issues/54)). It also requires KeePass's "remember master password" option, and the error when that option is off is misleading ([#82](https://github.com/Angelelz/WinHelloUnlock/issues/82)). Its "database corrupted after delete key" report (#69) most likely runs the other way round: KeePass's own error points to a truncated file, and the plugin then wrongly suggested that the master key had changed ([#69](https://github.com/Angelelz/WinHelloUnlock/issues/69)). LockAssist had a real corruption path. A quick unlock with a missing key file let KeePass save the database under a wrongly rebuilt composite key ([LockAssist #4](https://github.com/Rookiestyle/LockAssist/issues/4)). Most "incompatible with KeePass 2.xx" reports were install mistakes, for example a renamed DLL that breaks KeePass's naming rule ([WHU #75](https://github.com/Angelelz/WinHelloUnlock/issues/75)).

KeePass 2.60 and 2.61 appear in KeePassWinHello error reports, but no issue identifies an API break. The reports also conflict: one user fixed 0x80098044 by going back from 2.61 to 2.60, while another sees it on both versions ([#130](https://github.com/sirAndros/KeePassWinHello/issues/130), [#120](https://github.com/sirAndros/KeePassWinHello/issues/120)). The upstream project has had no human maintainer activity since mid-2024. Its June 2026 pull requests were opened by a bot account and state that they were not tested on Windows Hello hardware ([PR #158](https://github.com/sirAndros/KeePassWinHello/pull/158)). A maintained, signed release channel would therefore stand out by itself.

### YubiKey users want a KeePassXC-compatible format that KeePass 2 lacks

The YubiKey complaints are about format lock-in and fragility. KeeChallenge stores an encrypted static secret in an XML file next to the database. Its tracker has 55 issues, 39 of them open. The 25 newest break down as follows: 6 breakages after KeePass or Windows updates, 3 about maintenance, 4 about key combinations and removal, and 2 about incompatibility with KeePassXC and the mobile apps ([issues](https://github.com/brush701/keechallenge/issues?q=is%3Aissue)). One November 2025 reply explicitly asks for a "KeeChallengeXC" ([#62](https://github.com/brush701/keechallenge/issues/62)). KeePassium describes KeeChallenge's secret as static and replayable, and lists KeePass 2 with KeeChallenge as the one combination it cannot open ([KeePassium KB](https://support.keepassium.com/kb/yubikey-keechallenge/)). OtpKeyProv users lose access when the HOTP counter drifts out of sync ([Nitrokey forum](https://support.nitrokey.com/t/keepass-otp-generierung-klappt-nicht-mehr/788)).

On the KeePassXC side, the request to lock the database when the YubiKey is removed has been open since 2019 and moved to v2.9.0 in September 2026. Maintainers worry about unsaved changes that need the key to be saved ([#3616](https://github.com/keepassxreboot/keepassxc/issues/3616)). Users have also reported lost changes when the key was absent during sync ([#10227, #10251](https://github.com/keepassxreboot/keepassxc/issues?q=yubikey+lock+removed)). KeePassXC's own challenge-response format is supported by KeePassDX, Keepass2Android, KeePassium and Strongbox ([KeePassium compatibility](https://support.keepassium.com/kb/yubikey-compatibility/)), so it is the format to target.

## Windows Hello can be called from .NET Framework 4.8, but two behaviours are undocumented

Three technical routes exist. Each has a documented weakness.

| Route | Used by | Strengths | Weaknesses |
|---|---|---|---|
| WinRT `KeyCredentialManager` + `RequestSignAsync`; signature → symmetric key | KeePassXC, WinHelloUnlock, KeePassProtectedKeyStore | Documented API; TPM generates and protects the key where one exists; the app never sees the private key ([MS Learn](https://learn.microsoft.com/en-us/windows/apps/develop/security/windows-hello)) | Works only if signatures are deterministic, which is undocumented; signing takes no window handle ([RequestSignAsync](https://learn.microsoft.com/en-us/uwp/api/windows.security.credentials.keycredential.requestsignasync)) |
| NCrypt with the "Microsoft Passport Key Storage Provider" (RSA decrypt) | KeePassWinHello | Real decrypt; window handle and custom prompt text | Depends on the undocumented `NgcCacheType` property ([MS Q&A](https://learn.microsoft.com/en-gb/answers/questions/2100684/undocumented-usage-of-ncrypt-api-for-microsoft-pas), [PR #157](https://github.com/sirAndros/KeePassWinHello/pull/157)); this is the route behind the 45-issue error cluster |
| `UserConsentVerifier` for-window interop | none for unlock | Window-parented prompt (build 22000+) ([MS Learn](https://learn.microsoft.com/en-us/windows/win32/api/userconsentverifierinterop/nf-userconsentverifierinterop-iuserconsentverifierinterop-requestverificationforwindowasync)) | Returns only a yes/no answer, so the Hello gesture is not bound to any key |
| DPAPI `ProtectedData` | KeePassAutoUnlock, WinKee | Documented, built into .NET 4.8 ([MS Learn](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.protecteddata)) | No user gesture: any code running as the user can decrypt |

**The KeyCredential route fits RamzX Unlock's TPM goal, but its key derivation rests on an undocumented property.** KeePassXC signs a random challenge, hashes the signature with SHA-256 and uses the result as an AES-256-GCM key. At unlock it signs the same challenge again, which only works if the signature comes out byte-identical ([WindowsHello.cpp](https://github.com/keepassxreboot/keepassxc/blob/develop/src/quickunlock/WindowsHello.cpp)). Microsoft's developer guide verifies Hello signatures with PKCS#1 v1.5 padding, which is deterministic per [RFC 8017](https://www.rfc-editor.org/rfc/rfc8017#section-8.2) ([Windows Hello guide](https://learn.microsoft.com/en-us/windows/apps/develop/security/windows-hello)). The `KeyCredentialManager` class page, however, says the format is "PKCS #1 RSA PSS", which is randomized ([KeyCredentialManager](https://learn.microsoft.com/en-us/uwp/api/windows.security.credentials.keycredentialmanager)).

KeePassXC has shipped this design since 2.7.0 in 2022. In about 70 issues reviewed, there was no group of reports of the kind non-deterministic signatures would cause. That suggests determinism holds in practice. KeePassXC's blobs live only in memory, though. RamzX Unlock's persisted blobs carry the extra risk that Windows changes the signature behaviour or replaces the key. This must be measured on the target build, and enrollment must check it every time.

**Window ownership is only partly solved by newer APIs.** `RequestCreateForWindowAsync(WindowId, …)` exists in the 26100 and 28000 SDK documentation, but it covers only key *creation*. No window-bound variant of `OpenAsync` or `RequestSignAsync` was found ([MS Learn](https://learn.microsoft.com/en-us/uwp/api/windows.security.credentials.keycredentialmanager.requestcreateforwindowasync)). A developer on Microsoft Q&A reports that KeyCredential prompts from non-UWP apps get their own taskbar icon and do not take focus ([MS Q&A](https://learn.microsoft.com/en-gb/answers/questions/2100684/undocumented-usage-of-ncrypt-api-for-microsoft-pas)). The most important single datum for this machine is [KeePassProtectedKeyStore #6](https://github.com/CSquared167/KeePassProtectedKeyStore/issues/6), opened 2026-10-18. On KeePass 2.61.1 (32-bit) and Windows 11 build 10.0.26300, the KeyCredential-based Hello prompt "appears and then closes right away", and on the auto-login path KeePass hangs. Until a spike on this machine proves otherwise, the recommended route has to be treated as possibly broken on build 26300.

**Build route without Visual Studio.** Microsoft documents `Microsoft.Windows.SDK.Contracts` as the way for .NET Framework 4.x projects to call WinRT ([MS Learn](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/winrt-apis-desktop-apps)). The package targets netstandard2.0, works with net461 through net481, requires PackageReference, and had its latest stable release on 2026-08-26 ([NuGet](https://www.nuget.org/packages/Microsoft.Windows.SDK.Contracts)). That makes the toolchain an SDK-style project built with `dotnet build`:

- `TargetFramework` set to `net48`;
- `Microsoft.NETFramework.ReferenceAssemblies` 1.0.3, so no targeting pack is needed ([NuGet](https://www.nuget.org/packages/Microsoft.NETFramework.ReferenceAssemblies));
- Contracts at version 10.0.26100.x or later if `RequestCreateForWindowAsync` is wanted;
- a non-copied reference to `KeePass.exe`.

The machine has dotnet *runtimes* only, so a .NET SDK must be installed first. It can be installed per user, without Visual Studio. The in-box .NET Framework `csc.exe` is a possible fallback, but it is limited to old C# and needs Windows metadata files. That path was not tested. Ship a DLL, not a PLGX. KeePass recommends DLLs because they can be Authenticode-signed ([keepass.info](https://keepass.info/help/v2_dev/plg_index.html)). Nobody has verified that the PLGX compiler resolves WinRT references, and WinHelloUnlock's author could not get it to work ([WHU #22](https://github.com/Angelelz/WinHelloUnlock/issues/22)).

The Contracts package is under Microsoft's proprietary Windows SDK licence. Whether any facade DLLs it pulls in must ship next to the plugin, and whether they may be redistributed, has not been checked. The goal is a single MIT DLL that needs nothing beside it.

**One more gap specific to .NET Framework 4.8 (inferred, to confirm):** the managed `AesGcm` class arrived with .NET Core 3.0, so net48 has no built-in AEAD class. There are two practical options. One is encrypt-then-MAC (AES-256-CBC plus HMAC-SHA256), which is the construction KeePass FIDO2 uses ([keepass-fido2](https://github.com/Helveg/keepass-fido2)). The other is calling CNG's GCM mode through P/Invoke. Avoid both of WinHelloUnlock's mistakes: it uses ECB mode and the raw signature as the key, with no MAC ([UWPLibrary.cs](https://github.com/Angelelz/WinHelloUnlock/blob/master/WinHelloUnlock/UWPLibrary.cs)).

## KeePass 2 offers enough public hooks to avoid reflection on private fields

KeePass's plugin contract is strict and well documented ([keepass.info](https://keepass.info/help/v2_dev/plg_index.html)):

- the DLL name must equal the namespace, so the plugin is `MiftawerkUnlock.dll` with namespace `MiftawerkUnlock`;
- the main class must be `<Namespace>Ext`, here `MiftawerkUnlockExt`;
- the Product Name field must be exactly "KeePass Plugin";
- the library must target .NET Framework;
- `UpdateUrl` can point to a version file signed with RSA/SHA-512.

The latest KeePass release is 2.61.1 (2026-05-01). The release notes for 2.60 to 2.61.1 list no plugin-API breaks. They do list repeated secure-desktop focus fixes and a new update banner inside the master-key prompt ([2.60](https://keepass.info/news/n251102_2.60.html), [2.61](https://keepass.info/news/n260304_2.61.html)). This machine runs 2.60, so test on 2.60 and on 2.61.1.

The hooks RamzX Unlock needs are public ([MainForm_Functions.cs](https://raw.githubusercontent.com/dlech/KeePass2.x/master/KeePass/Forms/MainForm_Functions.cs), [MainForm.cs](https://raw.githubusercontent.com/dlech/KeePass2.x/master/KeePass/Forms/MainForm.cs)):

- `MainForm.OpenDatabase(IOConnectionInfo, CompositeKey, bool)`, which accepts a ready-made key;
- `MainForm.LockAllDocuments()`;
- the `FileClosingPre`, `FileClosingPost` and `FileClosed` events, which carry a locking flag;
- the `MasterKeyChanged` and `FileSaving*` events;
- KeePass's own session-lock handler, which locks on Windows lock, session end or user switch when `WorkspaceLocking.LockOnSessionSwitch` is set.

The key prompt (`KeyPromptForm`) registers with `GlobalWindowManager`, which is how quick-unlock plugins detect it. Its `CompositeKey` property is read-only, though, and its static `ShowDialog` is internal ([KeyPromptForm.cs](https://raw.githubusercontent.com/dlech/KeePass2.x/master/KeePass/Forms/KeyPromptForm.cs)). KeePassWinHello works around this by writing into private fields through reflection and by temporarily editing KeePass's secure-desktop settings. It also closes KeePass message boxes by matching the window class and title ([KeyManager.cs](https://github.com/sirAndros/KeePassWinHello/blob/master/src/KeyManagement/KeyManager.cs)). That coupling is behind regressions such as #92 and #107. A cleaner pattern is to cancel the prompt and call `OpenDatabase` with the reconstructed key. Two points are still unverified: how to read the locked document's connection info without private members, and whether the key prompt can be pre-empted cleanly. Both go in the spike.

For the YubiKey phase, KeePass's `KeyProvider` base class has these properties ([KeyProvider.cs](https://raw.githubusercontent.com/dlech/KeePass2.x/master/KeePassLib/Keys/KeyProvider.cs)):

| Property | Default |
|---|---|
| `Exclusive` | false |
| `DirectKey` | false; returning true is "highly discouraged" |
| `GetKeyMightShowGui` | true |
| `SecureDesktopCompatible` | false |

`KdbxFile.Save` generates a new master seed and re-randomizes the KDF parameters **on every save** ([KdbxFile.Write.cs](https://raw.githubusercontent.com/dlech/KeePass2.x/master/KeePassLib/Serialization/KdbxFile.Write.cs)). That one line decides the YubiKey design (see the requirements section). The source mirror is dated 2003–2025, so it may lag behind 2.61.1. Verify against the official source ZIP.

## Windows Hello here is a convenience lock, not a second factor

The security framing must rest on Microsoft's own statements:

- **PIN is a mandatory fallback.** It cannot be turned off while biometrics stay enabled, and repeated biometric failures fall back to it ([WHfB FAQ](https://learn.microsoft.com/en-us/windows/security/identity-protection/hello-for-business/faq)).
- **The API cannot force a modality.** KeePassXC confirms this ([#13734](https://github.com/keepassxreboot/keepassxc/issues/13734)), and a KeePassWinHello maintainer-side comment says no NCrypt property selects face, fingerprint or PIN ([PR #145](https://github.com/sirAndros/KeePassWinHello/pull/145)).

So **anyone who has the Windows session and knows the Hello PIN can unlock the database while a record is valid.** For that period, RamzX Unlock replaces the master password with the Windows Hello PIN or biometric. It adds no second factor. A WinHelloUnlock user put the trade-off plainly: the fallback is the PC's PIN, not the database password ([WHU #53](https://github.com/Angelelz/WinHelloUnlock/issues/53)). KeePassXC's maintainer says the same about KeePassXC's own feature: the Hello dialog "is NOT protecting your database" ([#12376](https://github.com/keepassxreboot/keepassxc/issues/12376)).

The protection that remains real is narrower, and it can be stated precisely:

- A copied record file is useless without this user's Hello key.
- That key is generated and held by the TPM where one exists, with software protection otherwise. Apps never receive the private key ([Windows Hello guide](https://learn.microsoft.com/en-us/windows/apps/develop/security/windows-hello)).
- A PIN reset deletes the key, so records fail safe and the user falls back to the master password ([WHfB FAQ](https://learn.microsoft.com/en-us/windows/security/identity-protection/hello-for-business/faq)).

The plugin can check whether the key is TPM-backed only through attestation, which is available only with TPM 2.0. If TPM backing is the selling point, the plugin should show the attestation result rather than assume it.

Two limits must be disclosed:

- **The key is scoped to the user, not to the app.** A Microsoft Q&A test showed an unpackaged app opening and using another app's credential of the same name after a Hello gesture. A moderator called per-user scoping "by design" for apps outside an AppContainer ([MS Q&A](https://learn.microsoft.com/en-us/answers/questions/5912130/what-is-the-security-boundary-of-windows-hello-key)). Same-user malware that tricks the user into one Hello approval can therefore recover the record key. KeePassWinHello's README advises treating an unexpected Hello prompt like an unexpected UAC prompt ([README](https://github.com/sirAndros/KeePassWinHello/blob/master/ReadMe.md)). RamzX Unlock should give the same warning.
- **Same-user malware can already read KeePass's memory after an unlock.** No quick-unlock design defends against that.

Dominik Reichl asked a 2019 plugin author how a Hello plugin differs from KeePass's built-in Windows User Account option ([SourceForge](https://sourceforge.net/p/keepass/discussion/329220/thread/2608a85e0e/)). For RamzX Unlock the honest answer is: it requires a fresh Hello gesture for every unlock, it uses a TPM-held key where a TPM exists, and it expires. It is not stronger against an attacker who has both the logged-in session and the PIN.

**The biometric privacy statement can be strong and still accurate.** Microsoft states that enrollment data is device-specific, stored locally as an encrypted template database, "does not leave the device or roam", and is accessible to no process other than Windows Hello ([WHfB FAQ](https://learn.microsoft.com/en-us/windows/security/identity-protection/hello-for-business/faq)). The plugin receives only a signature, or a failure status. That supports a privacy-notice sentence such as: RamzX Unlock does not receive, store or transmit biometric data; recognition happens entirely inside Windows Hello, per Microsoft's documentation. Whether that settles every GDPR Art. 9 question is a legal judgement outside this research. Under UWG §5, marketing should stick to such checkable statements ("uses a TPM-held key where present, per Microsoft") and avoid comparative claims like "most secure" or "safer than KeePassXC".

## Conclusion: one architecture and one first spike

**Recommendation.** Build RamzX Unlock as a **quick-unlock layer over an unchanged KeePass master key**, in five parts:

1. The plugin creates one plugin-named KeyCredentialManager key, held by the TPM where one exists.
2. That key signs a random challenge stored with each record.
3. The signature is passed through HKDF and becomes the key for authenticated encryption of the database's derived key components.
4. The record lives only as ciphertext in a local, DPAPI-wrapped, non-roaming file with an absolute X-day expiry and a boot stamp. It is written only at enrolment and at manual unlock.
5. KeePass's own session lock handles "lock when Windows locks".

Add the YubiKey later as a **separate KeyProvider** that makes the YubiKey a real KDBX4 composite-key component in KeePassXC's format, with save-time re-challenge and a mandatory test-unlock. Do not build it as a second quick-unlock method.

This keeps the Hello path on documented APIs and keeps every Hello failure fail-safe. It confines data-loss risk to the YubiKey save path, where it can be fenced with round-trip tests. Keep the NCrypt Passport route only as plan B, if experiment 1 or 2 fails. It offers window ownership, but its undocumented properties sit behind the largest complaint cluster in this field.

**First prototype step.** Install a .NET SDK per user, without Visual Studio. Then build a throwaway `MiftawerkUnlock.dll` targeting net48, referencing Microsoft.Windows.SDK.Contracts 10.0.26100.x and KeePass.exe, with a single "Windows Hello self-test" menu item. The self-test should:

- check `IsSupportedAsync`;
- create the credential with `FailIfExists`, or open it if it exists;
- read the attestation status;
- sign one stored 32-byte challenge three times;
- compare the signatures and verify them against the public key under PKCS#1 v1.5 and under PSS;
- log the status codes, timings and whether the Hello window held the foreground.

Build the same code as a console exe. Run both on build 26300 with face, fingerprint and PIN, with KeePass in the foreground and in the tray, and repeat after a KeePass restart, sleep, a Fast Startup shutdown and a real reboot. If the prompt stays open and the signatures match, the architecture holds and product work can start. If the prompt closes immediately, as in KeePassProtectedKeyStore #6, or the signatures differ, the sign-derived envelope cannot work on this machine, and plan B has to be evaluated before any feature code is written.
